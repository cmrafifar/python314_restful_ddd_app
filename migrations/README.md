Generic single-database configuration.# Database Migrations — Alembic

This directory contains version-controlled MySQL database schema migrations managed by **Alembic**, the migration tool for SQLAlchemy.

## 1. Overview

Alembic tracks database schema changes through ordered Python revision scripts.

| Component | Purpose |
|---|---|
| `alembic.ini` | Alembic configuration, located in the project root |
| `migrations/env.py` | Configures database connectivity and SQLAlchemy metadata |
| `migrations/versions/` | Versioned schema migration scripts |
| `migrations/script.py.mako` | Template used to generate revision files |
| `alembic_version` | MySQL table recording the current applied revision |

We use:

- Python 3.14 and `uv`
- SQLAlchemy 2
- Alembic
- MySQL 8.4
- Podman Compose on Fedora Linux

**Architecture:** Database migrations and SQLAlchemy models belong to the infrastructure layer. Domain entities and application services must remain independent of Alembic and SQLAlchemy.

All Alembic commands below run from the project root unless otherwise specified.

## 2. Local development setup

### Start MySQL

```bash
podman compose up -d mysql
```

Verify the container:

```bash
podman compose ps
```

Check the logs if needed:

```bash
podman compose logs mysql
```

Our Compose configuration exposes MySQL on `127.0.0.1:3307` for access from the Fedora host.

Inside the Podman Compose network, MySQL is accessible as `mysql:3306`.

### Configure database environment variables

Configure the ignored `.env` using `.env.example` as described in
[development](../docs/development.md#local-api-and-database). Host settings use port 3307.
Load this file explicitly when executing Alembic from the Fedora host:

```bash
uv run --env-file .env alembic current
```

These credentials are for local development only. Do not commit production credentials or secrets.

Our `migrations/env.py` obtains database settings through `get_settings()` and passes them to the shared SQLAlchemy database engine factory.

The commands below assume the intended `APP_DB_*` settings are exported. Alternatively, add
`--env-file .env` after `uv run` for development migration commands. Exported variables take
precedence over file values. Container environment variables are not automatically available
on the host.

Integration tests use the same migration history in a separate MySQL service. Run
`./scripts/test_integration.sh` to provision that service, migrate `bookstore_test`, check drift,
and run its tests. See [testing](../docs/testing.md#mysql-integration-setup) for `.env.test` setup.

## 3. Initialize Alembic

Run only once when initially setting up a new project:

```bash
uv run alembic init migrations
```

This generates the migration directory, configuration files, and revision template.

**Do not rerun this command** after Alembic has been initialized. Existing project contributors should use the committed migration configuration.

## 4. Creating a migration

After changing a SQLAlchemy persistence model, generate a revision:

```bash
uv run alembic revision --autogenerate -m "create books table"
```

The `--autogenerate` option compares:

1. The current database schema.
2. The SQLAlchemy `Base.metadata` definitions registered by imported ORM models.

Alembic generates a candidate migration containing the detected differences.

Example revision:

```python
def upgrade() -> None:
    op.create_table(
        "books",
        sa.Column("id", sa.String(36), nullable=False),
        sa.Column("isbn", sa.String(13), nullable=False),
        sa.Column("title", sa.String(255), nullable=False),
        sa.Column("author", sa.String(255), nullable=False),
        sa.PrimaryKeyConstraint("id"),
        sa.UniqueConstraint("isbn", name="uq_books_isbn"),
    )


def downgrade() -> None:
    op.drop_table("books")
```

The actual generated revision also contains revision identifiers and imports.

### Important: Review autogenerated migrations

Alembic autogeneration is not a substitute for engineering review.

It may not correctly infer:

- Column and table renames.
- Data transformations and backfills.
- All constraint and index changes.
- Complex database-specific behavior.
- Destructive changes requiring a multi-release rollout.

For example, renaming a column may be detected as deleting the old column and adding a new one. Applying that migration without modification could destroy data.

**Always review and, where necessary, manually edit the generated revision before executing it.**

### Creating an empty revision

```bash
uv run alembic revision -m "backfill book metadata"
```

Without `--autogenerate`, Alembic generates an empty migration script.

Use this for manually designed migrations, including custom SQL and controlled schema changes.

## 5. Applying migrations

Apply all pending migrations:

```bash
uv run alembic upgrade head
```

`head` refers to the latest revision in the selected Alembic revision lineage.

Apply migrations through a specific revision:

```bash
uv run alembic upgrade <revision_id>
```

Apply exactly one next revision:

```bash
uv run alembic upgrade +1
```

For projects with multiple migration branches, an unqualified `head` may be ambiguous. Alembic can have multiple heads that require explicit selection, merging, or use of `heads`.

## 6. Inspecting migration state

### Show the current database revision

```bash
uv run alembic current
```

This displays the revision currently recorded in the database.

### Show migration history

```bash
uv run alembic history --verbose
```

This displays the available revisions and their relationships.

### Show the latest revisions

```bash
uv run alembic heads
```

This is especially useful when working with multiple development branches.

### Show a specific revision

```bash
uv run alembic show <revision_id>
```

### Verify the schema is synchronized

```bash
uv run alembic check
```

This checks whether Alembic autogeneration would detect new schema changes relative to the current database.

It is useful in CI but has the same detection limitations as `--autogenerate`. It does not prove that all data or database behavior is correct.

## 7. Inspecting the actual MySQL schema

List the tables:

```bash
podman compose exec mysql \
  mysql -u bookstore -p bookstore \
  -e "SHOW TABLES;"
```

Inspect the `books` table:

```bash
podman compose exec mysql \
  mysql -u bookstore -p bookstore \
  -e "SHOW CREATE TABLE books\G"
```

Inspect Alembic's stored revision:

```bash
podman compose exec mysql \
  mysql -u bookstore -p bookstore \
  -e "SELECT * FROM alembic_version;"
```

The `-p` option prompts for the MySQL password. Enter the local development password when requested.

Note that `alembic_version` records revision state. It is not a general-purpose migration execution log.

## 8. Downgrading migrations

Downgrade one revision:

```bash
uv run alembic downgrade -1
```

Downgrade to a specific revision:

```bash
uv run alembic downgrade <revision_id>
```

Downgrade all the way to the base revision:

```bash
uv run alembic downgrade base
```

**Warning:** Downgrades can destroy data.

For example:

```python
def downgrade() -> None:
    op.drop_table("books")
```

This removes the table and its records.

Restoring the previous schema does not necessarily restore the previous data.

Do not assume downgrades are safe merely because Alembic supports them.

In production, a forward-fix or a separately planned restoration procedure may be safer.

## 9. Safe schema evolution: Expand → Backfill → Contract

Adding a required column to a table that already contains data requires special care.

Suppose we want to add `published_at` to a large `books` table.

### Phase 1: Expand

Add the column as nullable:

```python
op.add_column(
    "books",
    sa.Column(
        "published_at",
        sa.DateTime(),
        nullable=True,
    ),
)
```

Deploy application code capable of handling the column being nullable and, when appropriate, populating it for new records.

### Phase 2: Backfill

Populate existing records with valid values.

Large backfills should generally be:

- Batched to limit lock duration and transaction size.
- Idempotent and restartable.
- Monitored for failures and database load.
- Designed to preserve business correctness.

Do not invent default business values merely to satisfy database constraints.

### Phase 3: Contract

After all records contain valid data and all running application versions support the new schema:

```python
op.alter_column(
    "books",
    "published_at",
    existing_type=sa.DateTime(),
    existing_nullable=True,
    nullable=False,
)
```

Apply this as a subsequent migration.

For production, first check whether the operation requires a table rebuild, obtains disruptive metadata locks, or needs an online schema-change strategy.

This multi-phase approach is especially important during rolling application deployments.

## 10. MySQL transaction and DDL nuances

MySQL DDL behavior differs from ordinary transactional DML.

Statements such as:

```sql
CREATE TABLE books (...);
ALTER TABLE books ...;
DROP TABLE books;
```

generally cause implicit commits.

Consequently:

- Multiple schema operations may not form a single rollback-safe transaction.
- A migration can partially succeed before a later operation fails.
- SQLAlchemy transaction context managers do not make MySQL schema migrations universally atomic.
- Database-native atomic DDL support does not mean a multi-statement Alembic migration is atomic.

For MySQL 8, some individual DDL statements provide crash-safe atomic behavior, but this does not provide general transactional rollback of arbitrary schema migrations.

Always inspect migration operations before executing them against important databases.

## 11. Offline migration SQL

Alembic can generate SQL without applying it directly to the database:

```bash
uv run alembic upgrade head --sql > migration.sql
```

This is useful for reviewing SQL or executing migrations through controlled database change processes.

Offline SQL generation requires a properly configured dialect and migration environment. It may not support migrations that require querying existing database data.

Inspect the generated `migration.sql` before using it.

## 12. Marking an existing database revision

Alembic supports:

```bash
uv run alembic stamp head
```

This updates recorded revision state **without executing the migration operations**.

Use it only when the database schema is already known to match the target revision, such as during carefully controlled adoption of Alembic for an existing database.

Incorrect stamping can make Alembic believe that schema changes have been applied when they have not.

Never use `stamp` merely to silence a failing migration.

## 13. SQLAlchemy metadata registration

Our `migrations/env.py` must import all ORM models before Alembic inspects `Base.metadata`.

For example:

```python
from bookstore_api.infrastructure.persistence.base import Base
from bookstore_api.infrastructure.persistence.models.book import BookModel

target_metadata = Base.metadata
```

The model import registers its table definition with SQLAlchemy's declarative metadata.

If a model is not imported, Alembic may not detect its table or changes.

As the application grows, prefer a centralized model-import module rather than scattering registration imports throughout migration configuration.

## 14. Development workflow

For routine schema changes, follow this process:

1. Update the SQLAlchemy persistence model.
2. Generate a candidate revision with `--autogenerate`.
3. Review and edit `upgrade()` and `downgrade()`.
4. Inspect data compatibility and potential locking implications.
5. Apply the migration to the local MySQL database.
6. Verify the actual schema and migration revision.
7. Run `alembic check` and relevant tests.
8. Commit the migration and associated model changes together.

Typical commands:

```bash
# Start MySQL
podman compose up -d mysql

# Generate migration
uv run alembic revision --autogenerate -m "describe schema change"

# Review the generated revision before proceeding

# Apply migrations
uv run alembic upgrade head

# Verify migration state
uv run alembic current
uv run alembic check

# Run tests and static analysis
uv run pytest
uv run basedpyright
uv run ruff check .
```

## 15. Production guidelines

When we introduce AWS and Kubernetes deployment, we will enforce additional practices:

- Run migrations as a controlled deployment operation, not automatically in every application worker.
- Prevent concurrent migration runners from modifying the same schema.
- Ensure migrations are compatible with rolling application deployments.
- Use separate database credentials with appropriate migration privileges.
- Never expose production database passwords through committed configuration.
- Take backups or establish recovery procedures before destructive operations.
- Review MySQL metadata locks and online DDL support.
- Monitor migrations and large data backfills.
- Prefer independently deployable, backward-compatible schema changes.

## 16. Book version-counter migration

Revision `8c214e7a93b0` follows `46da991b1999` and adds the nonnullable integer `version`
column with a server default of 1. Existing rows receive version 1. Title and author columns
remain `VARCHAR(255)`; the application now enforces title length 100 and author length 80.
The migration does not truncate text or narrow those columns.

Before applying the revision, inspect existing records using the target database's SQL client:

```sql
SELECT id, CHAR_LENGTH(title) AS title_length, CHAR_LENGTH(author) AS author_length
FROM books
WHERE CHAR_LENGTH(title) > 100 OR CHAR_LENGTH(author) > 80;
```

Review and correct incompatible records deliberately before retrying. The online upgrade runs
the equivalent count check and raises before adding the column if it finds incompatible text.
Offline SQL rendering skips that query because no connection exists; run this preflight
separately before executing rendered SQL. Coordinate writes during preflight and deployment
so older writers cannot introduce incompatible records after the check.

`server_default=sa.text("1")` supplies a SQL expression, yielding `DEFAULT 1`. The Python
string contains SQL source; it does not change the column from `Integer` to a text type.
This follows SQLAlchemy's
[server-default pattern](https://docs.sqlalchemy.org/en/20/core/defaults.html#server-invoked-ddl-explicit-default-expressions).
The ORM's separate `default=1` handles inserts through SQLAlchemy; the server default also
handles inserts that omit the column outside the ORM.

With database settings configured, apply and inspect the revision from the repository root:

```bash
uv run alembic upgrade head
uv run alembic current
uv run alembic check
```

Apply the migration before starting application code that selects or writes `version`. Check
the actual table and run the MySQL integration suite; file presence or offline SQL alone does
not prove application, existing-data compatibility, or concurrent-write behavior. The isolated
test workflow is `./scripts/test_integration.sh`; see [testing](../docs/testing.md).

To review only this revision's SQL without connecting to MySQL:

```bash
uv run alembic upgrade 46da991b1999:8c214e7a93b0 --sql
uv run alembic downgrade 8c214e7a93b0:46da991b1999 --sql
```

Even offline rendering needs the environment-backed settings required by `migrations/env.py`.
Use local configuration without printing credentials. Rendering omits the data preflight.

Downgrading to `46da991b1999` drops `version` and loses all counters while preserving the
other columns. Stop version-aware application workers before downgrading and deploy compatible
code before resuming. Reapplying initializes counters to 1; invalidate previously issued ETags
because old version-1 tags could match again. A downgrade does not relax the newer application's
text rules. MySQL DDL can commit implicitly; do not assume transaction rollback restores a
partially applied schema change. Review backups and recovery before executing a downgrade.

Live MySQL migration and concurrency verification remains user-owned for the current lesson.
Local static checks, HTTP tests with fakes, and SQL rendering must be reported separately.
