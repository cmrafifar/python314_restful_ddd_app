# Books Domain

Read before changing book behavior, validation, or terminology. This document describes implemented rules separately from unresolved business meaning.

## Chosen exercise scope

This is a contrived bookstore catalog for learning Python and its ecosystem. A Book represents a particular edition in one format, such as a paperback edition. It does not represent an individual physical copy or a title spanning all editions.

The catalog has one record per ISBN. Its UUID identifies the catalog record independently of its bibliographic identifier. This defines the intended business meaning of existing fields; it adds no new enforcement or operations. Inventory, ordering, lending, and pricing remain outside the current exercise.

See [decision 0001](../decisions/0001-learning-strategy.md) for the learning strategy behind this scope.

## Ubiquitous language

| Term | Current meaning |
|---|---|
| Book | Catalog record for one edition in one format, with a UUID, ISBN, title, and author text |
| Book ID | UUID identifying the record, generated by `Book.create` |
| ISBN | Immutable value object holding a validated 13-digit string |
| Title | Book title text, trimmed and validated by the entity |
| Author | A single text field; there is no separate author entity |
| Create book | Register a book whose ISBN is not already present |
| Rename book | Change the title on a domain object; not an application or HTTP operation yet |
| Repository | Application port for finding books by ID or ISBN and adding a book |
| Unit of work | Application port grouping repository work with an explicit commit |

## Implemented invariants

### ISBN

[`ISBN`](../../src/bookstore_api/domain/books/isbn.py) is a frozen, slotted dataclass with equality by value.

- Input must contain exactly 13 ASCII decimal digits.
- The final digit must match the checksum calculated with alternating weights of 1 and 3 over the first 12 digits.
- Hyphens, spaces, ISBN-10 strings, and non-ASCII digits are rejected. The object does not normalize input.
- The implementation does not enforce a `978` or `979` prefix or verify assignment by an ISBN authority.

Examples: `9780132350884` is accepted; `9780132350885` fails its checksum; `12345` fails its length requirement.

### Book

[`Book`](../../src/bookstore_api/domain/books/book.py) validates title and author on construction. `rename` applies the same title validation.

- Leading and trailing whitespace is removed with `strip()`.
- The resulting text must contain between 1 and 255 characters, inclusive.
- Internal whitespace is preserved.
- `Book.create` generates a UUID using `uuid4`.
- Reconstruction supplies the existing UUID rather than calling `create`.

For example, title `"  Clean Code  "` becomes `"Clean Code"`; a whitespace-only title raises `ValueError`. The same rules apply to author text.

The class exposes mutable `id` and `isbn` attributes. Stronger immutability is not currently enforced. Use explicit domain behavior for intended changes rather than treating public attributes as an update API.

### Creation and uniqueness

[`CreateBookService`](../../src/bookstore_api/application/books/create_book.py) checks ISBN uniqueness through its repository. A duplicate causes `BookAlreadyExistsError`, with no add or commit requested by the service.

On success, the service adds one book, commits, and returns its ID. Title/author failures occur inside the unit-of-work context; ISBN validation occurs before entering it.

The [`books` table](../../src/bookstore_api/infrastructure/persistence/models/book.py) also has a unique ISBN constraint. A concurrent duplicate can pass the preliminary lookup and fail at commit. That database failure is not yet translated into the application error.

## Open domain questions

These questions are not requirements or authorization to add behavior:

- Will multiple authors require richer modeling, or remain display text?
- Should the system normalize formatted ISBNs, accept ISBN-10, or enforce ISBN prefixes?
- Are ISBN and record identity ever allowed to change?
- What future operations, if any, need inventory, pricing, deletion, or availability rules?

Resolve a question when a concrete use case needs it. Record the chosen meaning here and any consequential design choice in [decision records](../decisions/README.md).
